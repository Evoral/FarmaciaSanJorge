# Design — chat-ayuda

Spec: `specs/chat-ayuda/spec.md` (CA1–CA14). Decisions and scope: `proposal.md`.

## Shape

The guide is **global** (same for every tenant, versioned with the code); authorization is **per tenant**
(`session.permisos` comes from the tenant's custom roles). The request always runs inside a tenant session.

One chat turn, orchestrated by the thin Server Action (`modules/ayuda/ui/actions.ts` — moved from `app/(app)/ayuda-actions.ts` because the 22 existing modules keep their actions in `modules/<m>/ui/actions.ts`, and the chat UI in `modules/ayuda/ui/` must not import from `app/`):

```
client: { conversacionId, pregunta, historial[≤6], foco?: entradaId }
  │
1. consultarAyuda (defineQuery + prepare)       no DB; LLM calls outside any transaction
     permitidas = filtrarGuia(GUIA, session.permisos)          // CA3, domain, pure
     foco       = foco ∈ permitidas ? foco : null               // CA7, revalidated
     salida     = gemini(armarContexto(permitidas, foco, historial, pregunta), schema(ids(permitidas)))
     if salida.necesitaDetalle && salida.entradaId ≠ foco:      // CA8, second and last call
       salida   = gemini(armarContexto(permitidas, salida.entradaId, ...), schemaSinDetalle)
     return resolverRespuesta(salida, permitidas)               // CA6: ruta from the guide
2. registrarConsultaAyuda (defineCommand)       tx: INSERT pregunta, respuesta, entrada_id, resultado → row id
     (also on provider failure, with resultado = 'error', before showing the CA11 message)
3. calificarRespuestaAyuda (defineCommand)      later, on "¿Te sirvió?": UPDATE util on the caller's own row (CA14)
```

Why the LLM call and the insert are separate use cases: the pipeline has no command with network I/O outside the
transaction, and an LLM call (up to ~10 s) must not hold a pooled connection. `defineQuery` + `prepare` is the
existing pattern for that (`shared/usecase.ts`). Extending the pipeline is not worth it for this.

## Module layout

```
modules/ayuda/
  domain/
    guia.ts                 EntradaGuia type + invariants
    guia-entradas.ts        the content (global)
    filtrar-guia.ts         every required permiso must be held
    armar-contexto.ts       compact serialization + stable prompt order
    resolver-respuesta.ts   model output → { respuesta, entrada: { id, titulo, ruta } | null }
    consulta-ayuda.ts       resultado values
  application/
    consultar-ayuda.ts              query + prepare (ayuda.consultar)
    registrar-consulta-ayuda.ts     command (ayuda.consultar)
    calificar-respuesta-ayuda.ts    command (ayuda.consultar), own row only — CA14
  infrastructure/
    gemini.server.ts                SDK (@google/genai pinned 2.10.0), timeout, structured output, `import "server-only"`
    consulta-ayuda-repository.ts    Prisma access to fsj.consulta_ayuda
  ui/
    actions.ts                                  Server Actions (the 22 existing modules keep their actions in modules/<m>/ui/actions.ts, and modules/ayuda/ui/ must not import from app/)
    chat-ayuda.tsx, chat-ayuda-container.tsx    chat (presentational + client state)
app/(app)/
  app-shell.tsx             mounts the chat when can(session, "ayuda.consultar") && key configured
```

`domain/` imports `Permiso` as a type from `@/shared/auth/authorize`. Both commands declare
`audit: { skip: true, reason: "fsj.consulta_ayuda is itself the record" }`.

## Guide data model

```ts
type EntradaGuia = {
  id: string;                    // stable slug, e.g. "recetas.cargar" — the model's enum value
  titulo: string;                // "Cargar receta"
  permisos: readonly Permiso[];  // ALL required (CA3); typed: a renamed permiso breaks the build
  ruta: string;                  // static app route, no dynamic segments: "/recetas/nuevo"
  pasos: string;                 // one short line: where + which button. Always sent
  detalles?: readonly { tema: string; texto: string }[];  // sent only for the entry in focus
  spec?: string;                 // openspec/specs/<spec> it was derived from
};
```

## Log table — `fsj.consulta_ayuda`

| Column | Notes |
|---|---|
| `id` uuid PK, `tenant_id` uuid | tenant-scoped, RLS like every tenant table |
| `usuario_id` uuid FK | session user (in a cuenta de sector: the account) |
| `conversacion_id` uuid | generated by the client per chat session; groups turns to see follow-ups |
| `pregunta` text (≤300) | |
| `respuesta` text null, `entrada_id` text null | what the chat showed and the entry it pointed to |
| `resultado` text | `respondida` \| `fuera_de_opciones` \| `error` (CHECK) |
| `util` boolean null | CA14 |
| `created_at` timestamptz | |

- Index: `(tenant_id, created_at)` for the owner's review.
- Grants to `fsj_app`: `SELECT`, `INSERT`, and **column-level** `UPDATE (util)` only. No `DELETE`. Everything else is
  immutable at the DB level.
- Ownership: `calificarRespuestaAyuda` filters by `usuario_id = session.usuario.id`; any other row is "not found".

## Who sees the log (CA13)

- **Platform owner only.** No use case lists consultas, so no tenant user — ADMINISTRADOR and DT included — can see
  them. Until the platform admin panel exists, the owner reviews through the Supabase SQL editor (owner role, bypasses
  RLS), e.g. unanswered or unhelpful turns:

  ```sql
  SELECT created_at, tenant_id, conversacion_id, pregunta, respuesta, entrada_id, resultado, util
  FROM fsj.consulta_ayuda
  WHERE resultado <> 'respondida' OR util = false
  ORDER BY created_at DESC;
  ```

- The platform admin panel (planned separately) needs a cross-tenant read path; that design belongs to that change,
  not this one. `DIRECT_URL` stays out of runtime code.

## Context budget (tokens)

| Part | Sent | Approx. |
|---|---|---|
| Fixed rules | always, first | ~300 |
| Index: one line per permitted entry (`id \| titulo \| pasos`) | always, sorted by id | ~40 per entry, ~4k for 100 |
| Details of the entry in focus | only when a focus exists | 200–400 |
| History (≤6 messages × ≤500 chars) + question (≤300) | always, last | ≤1k |

- **Order matters:** stable parts first so Gemini's implicit prefix cache applies; every session with the same
  permission set shares the prefix. No explicit cache (storage billed per hour, one per permission set).
- **Plain lines, not JSON**, for the index.
- **Output pricing:** output tokens, thinking included, are billed at $2.50 per 1M tokens ($0.30/1M standard input, $0.03/1M cached input).
- **Budget test:** the serialized index of the full guide stays under a fixed character limit.
- **Future swap point:** a `seleccionarContexto(permitidas, pregunta)` step between `filtrarGuia` and
  `armarContexto` if the guide outgrows the budget.

## Model call

- Official SDK `@google/genai` pinned to `2.10.0` (no caret), used exclusively in `modules/ayuda/infrastructure/gemini.server.ts` with `import "server-only"`.
- Model: `gemini-2.5-flash` by default, overridable via optional `GEMINI_MODEL` env var.
- Thinking: `gemini-2.5-flash` cannot disable thinking. Set the lowest supported thinking level (`low`) explicitly on every call. Output tokens, thinking included, are billed at the output rate ($2.50/1M).
- Low temperature; timeout (~10 s) configured via SDK request options or an abort signal. Timeout or non-2xx → typed error → CA11.
- Structured output: configured using the SDK's JSON schema config with the per-request enum of permitted ids (`{ respuesta: string, entradaId: enum(ids of permitidas) | null, necesitaDetalle: boolean }`), re-parsed with zod on the server.
- The model never returns a route: `resolverRespuesta` maps `entradaId` → `ruta` (CA6).
- `entradaId: null` → the fixed CA4b card ("preguntale a tu director técnico o al administrador"), regardless of what
  the model wrote, with resultado `fuera_de_opciones`. The card never says whether the action exists for another role
  (the server does not know either: the model only saw permitted entries).

## Security

- **Authorization is deterministic**: `filtrarGuia` decides, never the model. Prompt injection can only make it pick
  a wrong entry among the ones the user may already see.
- **No tenant data** reaches the model (CA10); `consultarAyuda` does not read the DB.
- **Plain-text rendering** of model output (no markdown/HTML, never `dangerouslySetInnerHTML`). "Ir a" uses the
  server-resolved `ruta` with `next/link`.
- **API key and model**: `GEMINI_API_KEY` and `GEMINI_MODEL` are both optional in `shared/env.ts`, server-only
  (blank → undefined; model defaults to `gemini-2.5-flash`); read only in `gemini.server.ts`. Paid tier key.
- **Paid-tier data terms (checked 2026-10-28)**:
  - Prompts and responses are not used to improve Google products on paid services (https://ai.google.dev/gemini-api/terms).
  - Google logs prompts and responses for a limited period, solely to detect policy violations and meet legal requirements (same URL). The usage policies state a 55-day retention for prompts and output, without separating paid from free use (https://ai.google.dev/gemini-api/docs/usage-policies). Whether this logging can be disabled: unverified.
  - No data-region option: the terms say data may be stored transiently or cached in any country where Google has facilities (https://ai.google.dev/gemini-api/terms). Whether another Google product offers regional residency: unverified, out of scope.
- **Input bounds** in zod: question ≤300, ≤6 history messages of ≤500, `foco` ≤64 chars (checked against the permitted
  set), `conversacionId` uuid.
- **Spend control** (User decision 2026-10-28): no in-app rate limit. Cloud Billing budgets only send alerts and do
  not stop requests; the hard limit is a per-day request quota override for the Generative Language API on the Cloud
  project, complemented by budget alerts. A dedicated Cloud project and key are recommended so quota and alerts are
  not shared with other apps. Abuse is bounded anyway: authenticated users only, bounded input, ≤2 calls per turn.
- **Stored questions may contain personal data** (an employee can type a patient's name): same tenant isolation as
  any patient data. Retention (User decision 2026-10-28): kept with no expiry until the platform owner decides to
  delete it, by hand; no purge job.

## Permission

`ayuda.consultar`, category `consulta`, **assignable** (User decision 2026-10-28): ADMINISTRADOR gets it automatically,
other roles through the role editor. The migration only inserts it into `fsj.permiso` (procedure:
`openspec/specs/roles-personalizables/spec.md`, "Cómo agregar un permiso nuevo"); no role rows.

Cuentas de sector (CA12): queries never ask for the PIN, and none of the chat's commands is a PIN action.

## Keeping the guide in sync

Unit tests (`tests/unit/ayuda-guia.test.ts`): unique ids; non-empty `permisos`, `titulo`, `pasos`; every `ruta`
resolves to a `page.tsx` under `app/(app)/` with no dynamic segment; every `spec` exists; index budget.

AGENTS.md gets one rule: a change to a user flow updates its guide entry in the same commit. Unhelpful answers and
`fuera_de_opciones` rows in the log are the input for new or better entries.

## Initial content

An agent drafts the entries from `openspec/specs/*` and the routes under `app/(app)/`, one per daily-use action, in
counter language. The user reviews them before merge; v1 does not need full coverage.
